# seekdb × hipVS 演讲提纲(讲者备注 · 纯要点)

> 用途:直接贴进 PPT 备注栏。每节对应一页幻灯片,3–5 个口语化要点,无代码。
> 主线:接通 AMD GPU 向量检索 → **诚实测量收益边界** → 单查无用、批量制胜。

---

## 封面
- 一句话:让 seekdb 向量索引**可选**跑在 AMD GPU(gfx1100),后端是 hipVS(cuVS 的 AMD 移植)。
- 两个卖点:默认构建零影响;GPU 按索引 opt-in,不确定就安全回退 CPU。
- 全场记住一句:**单条查询 GPU ≈ CPU;批量向量检索 GPU 才决定性更快。**

## 1. 背景:为什么要 GPU 向量检索
- 向量检索是 RAG / 语义搜索 / 推荐 / 去重的基础算子,做进 SQL 才能存算一体。
- seekdb 默认后端 VSAG(CPU HNSW),单查已经亚毫秒,基线不弱 —— GPU 要赢不容易。
- GPU 的机会在海量向量的**批量**相似度计算(相似度 JOIN、批量打分)。
- AMD 生态缺 cuVS,用 hipVS 补位;本次工作核心是"接起来 + 如实测量"。

## 2. 技术栈
- 五层:seekdb(SQL/存储)→ obvsag 抽象 → 桥接 so → hipVS(libcuvs)→ ROCm/GPU。
- 桥接层是纯 C,刻意隐藏所有 ROCm/cuVS 头,seekdb 主体不碰 GPU 细节。
- 硬件是 Radeon PRO W7900(gfx1100/RDNA3);官方 cuVS 只支持 CDNA,gfx1100 靠源码编译 hipVS,已全量测试通过。

## 3. 架构与集成缝
- seekdb 向量索引是两级:delta(增量)+ snapshot(快照),查询各查一份再合并。
- 后端选择缝在 obvsag C-API:同一接口,vsag 走 CPU、cuvs 走 GPU。
- 关键洞察:普通 HNSW 从不调 build_index;所以 GPU 钩子挂在 add_index(缓存向量)和 knn_search(惰性建 CAGRA 并服务)。

## 4. 两种用法
- 用法 A 声明式:建索引时加一个 lib=cuvs,这个索引就走 GPU,别的索引不受影响,不需要任何环境变量。
- 用法 B 批量算子:一条存储过程把 N 条探针一次喂给 GPU,这是 GPU 真正发力的入口。
- 关掉 GPU 或改回 lib=vsag,结果完全一致 —— 可回退、可对照。

## 5. 关键发现(全场最重要)
- 一开始假设 GPU 更快;端到端一测,单查 cuVS 反而慢 2.25 倍。
- 诊断:慢在未压缩 delta 的近线性全扫,不是 ANN 本身;压缩出快照后 APPROX 提速 37 倍,VSAG 快照 0.4ms/查。
- 结论:单查 GPU 追不上亚毫秒的 CPU HNSW —— 每次 GPU 调用的固定开销(显存分配、PCIe 传输、kernel 启动)吃掉了优势。
- 翻盘:把多条探针合并成一次 GPU 调用,固定开销被摊薄,批量 116×~263×。

## 6. 性能数据
- 一张表讲完:单查 cuVS 470 q/s ≈ CPU 快照;批量 nq=100 到 54,777 q/s(比逐条 116×、比最优 CPU 12×);桥接批量 nq=5000 到 263×。
- 批量红利来源就是摊薄每次调用的固定开销,单查永远追不上。
- 端到端 SQL 演示(10k 索引):N=100 还亏,N=1000 到 4.8×,N=4000 到 12×;CPU 墙钟线性涨,GPU 近乎持平。
- 交叉点大约在 N≈300 条探针以上。

## 7. 正确性与安全回退
- 原则:正确性优先于加速,任何不确定场景一律回退 VSAG,绝不给错答案。
- 带 WHERE 过滤:cuVS 返回后逐个按 VSAG 语义校验,发现被排除就回退。
- 删除后、非 L2(cosine/IP)、两次重建之间的新鲜度:都已门控并实测正确。
- 规模化召回 10k 行 recall@10 = 0.89,对齐真值。

## 8. 发布硬化
- 一个编译开关 OB_BUILD_CUVS;关掉(默认)时桥接根本不链接,行为与上游 VSAG 完全一致。
- DDL 层正式接受 lib=cuvs(dense L2 HNSW),IVF 拒绝;插件层标记走 GPU。
- 去掉了 PoC 期的硬编码路径、全局环境变量开关和调试 tracer;补了 CI 安全的契约测试。

## 9. 镜像固化 + Notebook 演示
- 做了一个自包含镜像,已推 ACR:拿到就能在 Jupyter 里体验批量提速。
- 所有 seekdb+hipVS 资产固化在 /seekdb_workspace,用户数据盘 /workspace 解耦,适配 k8s(PVC + Secret)。
- 一条 docker run 起容器,浏览器打开 notebook 自上而下跑,observer 由 notebook 单元启动,教学分步可见。

## 10. 现状与路线图
- 完整支持定义为 7 条(DDL 开关、增删改查正确、过滤正确、重启可用、百万级不 OOM、指标达标有回归、可选有文档)。
- 现状:happy path + 正确性 + 批量算子已打通,整体完成约 15–25%。
- M-A 正确性已完成;M-B 新鲜度完成、重启持久化暂缓(单机环境无法可靠制造快照);M-C 批量算子已交付;M-D 产品化大部分完成。
- 后续:快照重建 GPU 索引、常驻 GPU worker、批量算子缓存索引、扩展更多 GPU 型号。

## 11. 结论
- 接通了 AMD GPU 向量检索,默认零影响、按索引 opt-in、有安全回退。
- 诚实的收益边界:单查无收益;批量 116×~263×,端到端 SQL 约 12×。
- 又快又更准:默认参数下 cuVS 召回 0.88 高于 VSAG 0.64,批量与单查结果一致。
- 定位一句话:GPU 的价值在批量向量检索 / 更高召回 / 超大索引,而不是更快的单查。

## 预设问答
- 为什么单查不快?CPU HNSW 已亚毫秒,GPU 每次调用固定开销吃掉优势。
- GPU 到底值在哪?批量、更高召回、超大索引 + 相似度 JOIN。
- 默认会变慢或不稳吗?不会,编译开关关掉后与上游完全一致。
- 正确性怎么保证?不确定即回退 VSAG,过滤/删除/非 L2/新鲜度都逐一验证过。
